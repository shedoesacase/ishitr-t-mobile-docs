
## 1. Список акторов

| Актор              | Тип       | Описание                                                                                                                                                                                   |
| ------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Владелец**       | Первичный | Физическое лицо, управляющее семейной группой, способное менять состав группы, ограничивать лимиты, отслеживать потребление всех участников и передавать права владения другому участнику. |
| **Участник**       | Первичный | Участник семейной группы, на которого распространяются лимиты. Имеет возможность просматривать свое потребление и получать права владения.                                                 |
| Генератор          | Вторичный | Внешняя система. Генератор событий, связанных с потреблением трафика и минут.                                                                                                              |
| Система            | Первичный | Разрабатываемое приложение.                                                                                                                                                                |
| Пользователь       | Первичный | В рамках списка акторов под словом "Пользователь" подразумевается пользователь системы, не зависимо от его роли и участия в конкретной семейной группе.                                    |
| Сервис уведомлений | Вторичный | Сервис, отвечающий за отправку push-уведомлений.                                                                                                                                           |

## 3. Детализация сценариев 
### UC-01: Создание семейной группы
* **Актор:** Владелец
* **Предусловия:** Пользователь авторизован в приложении. У пользователя нет активной семейной группы (он не является владельцем или участником другой группы).
* **Постусловия:** Создана семейная группа, добавлены Участники (опционально). Запись о создании сохранена в историю (BR-09).
#### Основной сценарий: 
1. Пользователь выбирает "создать семейную группу" в приложении.
2. Система отображает экран добавления участников.
3. Пользователь добавляет в группу до трех человек, не включая себя.
4. Backend валидирует выбранных пользователей на соответствие BR-01 (проверяет по БД, что они не состоят в других группах).
5. Backend в рамках одной транзакции создает семейную группу в БД, присваивает инициатору роль Владелец, а приглашенным — роль Участник.
6. Backend создает запись в таблице истории изменений (BR-09).
7. Backend возвращает Мобильному приложению успешный ответ с данными созданной группы.
#### Исключения и альтернативные сценарии: 
* **2a. Пользователь не добавил других участников:** 
1. Система создает семейную группу с одним участником - Владельцем. 
2. Приложение предлагает Владельцу добавить других Участников.
* **4а. Выбранные пользователем люди уже участвуют в других семейных группах:**
1. Backend возвращает ошибку `USER_ALREADY_IN_GROUP` с указанием конкретных номеров/ID.
2. Мобильное приложение оповещает пользователя, что этих людей невозможно добавить, и предлагает выбрать других. Группа при этом не создается.

### UC-02: Установка индивидуального лимита Участнику
* **Актор:** Владелец, сервис уведомлений
* **Предусловия:** Семейная группа создана и активна. Владелец и Участник находятся в группе. Общий пакет услуг (минуты/интернет) > 0.
* **Постусловия:** Индивидуальный лимит Участника обновлен. Запись об изменении добавлена в историю. Если новый лимит меньше текущего расхода, доступ Участника к данному типу услуг мгновенно блокируется.
#### Основной сценарий: 
1. Владелец открывает экран управления семейной группой и выбирает Участника.
2. Владелец вводит новое значение лимита и нажимает «Сохранить».
3. Мобильное приложение отправляет REST-запрос (`PUT`) в Backend на изменение лимита.
4. Backend валидирует запрос согласно BR-13.
5. Backend в рамках одной транзакции сохраняет новый лимит в БД и мгновенно применяет его (BR-03).
6. Backend создает запись в таблице истории изменений (BR-09).
7. Backend возвращает Мобильному приложению успешный ответ с обновленными данными.
#### Исключения и альтернативные сценарии: 
- **5a. Новый лимит меньше текущего расхода Участника (BR-03):**
1. Backend сохраняет лимит, но мгновенно устанавливает `is_blocked` в `true` для данного типа услуг у этого Участника.
2. Backend публикует асинхронное событие `LimitExceeded` в брокер сообщений.
3. Сервис уведомлений (подписчик) получает событие и отправляет Push-уведомление Участнику о блокировке доступа.

### UC-03: Приглашение участника в семейную группу
* **Актор:** Владелец
* **Предусловия:** Семейная группа создана и активна. В группе менее 4-х человек. Пользователь, которого владелец хочет пригласить, не участвует в других семейных группах.
* **Постусловия:** В семейную группу добавлен новый участник. Запись добавлена в историю.
#### Основной сценарий: 
1. Владелец открывает экран управления семейной группой и выбирает "Добавить участника".
2. Мобильное приложение отправляет запрос в Backend для получения списка доступных пользователей из контактов.
3. Backend формирует список, сразу отфильтровывая из БД тех пользователей, которые уже состоят в других группах.
4. Мобильное приложение отображает отфильтрованный список. Владелец выбирает Участника.
5. Backend сохраняет нового участника в БД и выставляет его лимиты в статус "Не задан" (потребление идет из общего пакета без персональных ограничений, что эквивалентно 100%).
6. Backend создает запись в таблице истории изменений (BR-09).
7. Backend возвращает Мобильному приложению успешный ответ с новым Участником.
#### Исключения и альтернативные сценарии: 
- **1a. В группе уже есть 4 человека, включая владельца:**
1. Backend возвращает пользователю ошибку `USER_LIMIT_EXCEEDED`.
2. Мобильное приложение вместо выбора новых участников отображает надпись "Превышен лимит участников семейной группы".
- **2a. Искомого пользователя нет в контактах:**
1. Владелец вводит номер телефона пользователя в окне поиска.
2. Backend проверяет, существует ли этот номер телефона в БД.
3. Backend проверяет, состоит ли этот пользователь в других группах.
4. В случае, если пользователь не состоит в группе, он отображается в списке в приложении. В противном случае пользователь не отображается.

### UC-04: **Обработка входящего события потребления**
* **Актор:** Генератор
* **Предусловия:** Генератор опубликовал событие в брокер сообщений.
* **Постусловия:** Событие обработано, счетчики обновлены. Система инициирует проверку порогов потребления (UC-07) и проверку на аномальный рост (UC-08).
#### Основной сценарий: 
1. Генератор публикует событие (с уникальным набором полей в БД, расписаны будут позже) в брокер сообщений.
2. Backend забирает событие из очереди.
3. Backend проверяет идемпотентность (BR-04): ищет `event_id` в таблице уже обработанных событий.
4. Если события нет: Backend в рамках одной транзакции:
    - обновляет счетчик потребления пользователя и остаток общего пакета;
    - сохраняет `event_id` в таблицу обработанных событий.
5. Backend публикует асинхронное событие в шину событий.

#### Исключения и альтернативные сценарии: 
- **2a. Событие уже существует:**
1. Backend логирует и игнорирует событие.
2. Трафик/минуты не изменяются, транзакция не выполняется.

### UC-05: **Обработка запоздалого события потребления**
* **Актор:** Генератор
* **Предусловия:** Генератор опубликовал событие, произошедшее в прошлом.
* **Постусловия:** Событие обработано как актуальное. Система инициирует проверку порогов потребления (UC-07) и проверку на аномальный рост (UC-08).
#### Основной сценарий: 
1. Генератор публикует событие с меткой времени в прошлом в брокер сообщений.
2. Backend-обработчик забирает событие и проверяет идемпотентность по `event_id` (BR-04).
3. Согласно BR-15, Backend игнорирует исходную временную метку события и привязывает его к текущему моменту в рамках текущего расчетного периода.
4. Backend в рамках транзакции обновляет счетчики потребления и сохраняет `event_id`.
5. Backend публикует событие в шину событий.

#### Исключения и альтернативные сценарии: 
- **2a. Событие уже существует:**
1. Backend игнорирует событие.
2. Трафик/минуты не изменяются.
- **3a. Лимит пользователя оказался превышен из-за запоздалого события:**
1. Backend мгновенно уводит текущий баланс лимита трафика/минут в `0`.
2. Backend мгновенно блокирует пользователю доступ к этому типу связи (Переводит в статус `BLOCKED`).
3. Backend публикует событие в брокер сообщений для отправки Push-уведомления.

### UC-06: Расчет и отображение прогноза даты исчерпания пакета
* **Актор:** Владелец/Участник
* **Предусловия:** Группа существует, объем трафика/минут > 0.
* **Постусловия:** Рассчитан и отображен прогноз даты исчерпания пакета.
#### Основной сценарий: 
1. Пользователь открывает экран со статистикой использования трафика/минут.
2. 1. Мобильное приложение отправляет синхронный REST-запрос в Backend.
3. Backend рассчитывает прогнозируемую дату исчерпания пакета на основе BR-06.
4. Backend отправляет в приложение дату для отображения.
5. Мобильное приложение отображает данные: Владелец видит прогноз и среднее потребление каждого члена группы, Участник видит только свой прогноз и свое среднее потребление (согласно BR-12).

#### Исключения и альтернативные сценарии: 
- **2a. Невозможно посчитать примерную дату исчерпания пакета в первый день расчетного периода или в случае, если нет среднесуточного потребления:**
1. Backend отправляет в приложение в качестве прогнозируемой даты последний день расчетного периода *(Можно изменить на статистику предыдущего месяца, но текущий путь самый простой).*
2. Владелец или Участник просматривают дату, владелец видит среднее потребление каждого члена группы, Участник видит только свое среднее потребление.

### UC-07: Отправка уведомления о достижении порога потребления
* **Актор:** Система, сервис уведомлений
* **Предусловия:** Группа существует, объем трафика/минут > 0. Преодолен выставленный пользователем порог потребления минут/трафика.
* **Постусловия:** В случае, если преодолен порог общего трафика, push-уведомление рассылается всем участникам семейной группы. Если преодолен порог конкретного пользователя, push-уведомление присылается ему и Владельцу.
#### Основной сценарий: 
1. Сервис уведомлений получает событие из брокера сообщений.
2. Сервис проверяет, не было ли уже отправлено уведомление о достижении данного конкретного порога в текущем расчетном периоде.
3. Если порог преодолен впервые: Сервис формирует payload и отправляет запрос во внешний Push-шлюз.
4. Push-уведомление доставляется конкретному пользователю (при превышении личного порога) или всем участникам группы (при превышении общего порога, настроенного Владельцем).
5. Сервис уведомлений отправляет отдельное Push-уведомление Владельцу о факте преодоления порога участником.

### UC-08: Детекция аномального роста и отправка уведомления
* **Актор:** Система
* **Предусловия:** Группа существует, объем трафика/минут > 0. Произошел аномальный рост потребления трафика согласно BR-15.
* **Постусловия:** Владелец получил push-уведомление о количестве потребленного трафика с указанием Участника.
#### Основной сценарий: 
1. Backend фиксирует аномальное потребление трафика согласно BR-15.
2. Backend отправляет push-уведомление Владельцу.

#### Исключения и альтернативные сценарии: 
- **1a. Аномальное потребление трафика зафиксировано со стороны Владельца:**
1. Backend отправляет уведомление Владельцу, но вместо конкретного Участника указывает самого Владельца.

### UC-09: Выход участника из семейной группы
* **Актор:** Участник
* **Предусловия:** Группа существует. В группе, помимо владельца, присутствуют еще Участник(и).
* **Постусловия:** Участник покинул группу, его лимит аннулирован, а остаток распределяется согласно BR-08. Сохранена история изменений.
#### Основной сценарий: 
1. Участник выбирает "Покинуть группу" в настройках.
2. Мобильное приложение отправляет REST-запрос в Backend.
3. Backend проверяет роль пользователя.
4. Backend в рамках одной транзакции:
    - удаляет связь пользователя с группой;
    - аннулирует его индивидуальные лимиты;
    - пересчитывает доступный остаток общего пакета (возвращая неиспользованную долю участника с возможностью перераспределения);
    - создает запись в таблице истории изменений (BR-09).
5. Backend публикует асинхронное событие в брокер сообщений.
6. Сервис уведомлений получает событие и отправляет Push-уведомление Владельцу.

#### Исключения и альтернативные сценарии: 
- **2a. Попытку выхода совершает Владелец:**
1. Backend отклоняет запрос с ошибкой `OWNER_CANNOT_LEAVE`.
2. Мобильное приложение показывает подсказку "Владелец не может покинуть группу. Передайте права другому участнику или расформируйте группу".

### UC-10: Передача прав владельца группы другому участнику
* **Актор:** Владелец, Участник
* **Предусловия:** Группа существует, в группе больше 1 участника.
* **Постусловия:** Владелец передал права владения Участнику, Участник стал Владельцем, Владелец - Участником.
#### Основной сценарий: 
1. Владелец выбирает "Передать права владения" в списке участников.
2. Мобильное приложение отправляет запрос в Backend.
3. Backend сохраняет намерение и отправляет Push-уведомление целевому Участнику с кнопками «Принять» и «Отклонить».
4. Участник получает уведомление, открывает его и нажимает «Принять».
5. Backend в рамках одной транзакции меняет роли:
    - текущий Владелец становится Участником;
    - целевой Участник становится Владельцем.
6. Backend создает запись в таблице истории изменений (BR-09).
7. Backend возвращает успешный ответ обоим клиентам.

#### Исключения и альтернативные сценарии: 
- **4a. Участник отказывается от прав владения:**
1. Backend не меняет роли участников семейной группы.
- **4b. Целевой Участник успел выйти из группы (UC-09) или был исключен (UC-12) до момента подтверждения:**
1. Backend при попытке подтверждения возвращает ошибку `USER_NOT_IN_GROUP`.
2. Роли не изменяются. Владелец получает уведомление, что передача не состоялась.

### UC-11: Расформирование группы
* **Актор:** Владелец
* **Предусловия:** Группа существует, в группе больше 1 участника, включая Владельца.
* **Постусловия:** В группе остался только Владелец.
#### Основной сценарий: 
1. Владелец выбирает "Расформировать группу" в настройках.
2. Мобильное приложение отправляет запрос в Backend.
3. Backend возвращает запрос на подтверждение (диалоговое окно «Вы уверены? Все участники будут исключены»).
4. Владелец подтверждает расформирование.
5. Backend в рамках одной транзакции:
    - аннулирует все индивидуальные лимиты участников;
    - переносит остаток общего пакета на личный баланс Владельца;
    - удаляет связи всех участников с группой;
    - удаляет саму группу из БД;
    - создает финальную запись в таблице истории изменений (BR-09).
6. Backend публикует асинхронное событие в брокер сообщений.
7. Сервис уведомлений получает событие и рассылает Push-уведомления всем бывшим Участникам об исключении из группы.

#### Исключения и альтернативные сценарии:
- **4a. Владелец отменяет подтверждение:**
1. Мобильное приложение закрывает диалоговое окно. Запрос на Backend не отправляется.

### UC-12: Исключение участника из группы
* **Актор:** Владелец
* **Предусловия:** Группа существует, в группе больше 1 участника, включая Владельца.
* **Постусловия:** Участник удален из группы. Его личный лимит аннулирован. Неиспользованный трафик (доля в общем пакете) возвращен в общий пул (BR-08). Изменения записаны в историю (BR-09).
#### Основной сценарий: 
1. Владелец выбирает "Исключить участника" в списке участников.
2. Мобильное приложение отправляет запрос в Backend.
3. Backend возвращает запрос на подтверждение.
4. Владелец подтверждает исключение.
5. Backend в рамках одной транзакции:
    - удаляет связь Участника с группой;
    - аннулирует его индивидуальные лимиты;
    - пересчитывает доступный остаток общего пакета (возвращая неиспользованную долю участника с возможностью перераспределения);
    - создает запись в таблице истории изменений (BR-09).
6. Backend публикует асинхронное событие в брокер сообщений.
7. Сервис уведомлений рассылает Push-уведомления Владельцу и исключенному Участнику.

### UC-13: Сброс счетчиков при смене расчетного периода
* **Актор:** Система
* **Предусловия:** Группа существует, обновился расчетный период.
* **Постусловия:** Обновлены счетчики потребления, остаток сгорел, лимиты сохранены.
#### Основной сценарий: 
1. Backend в рамках одной транзакции для каждой группы:
    - архивирует статистику потребления за прошедший расчетный период;
    - обнуляет текущие счетчики потребления (общий и индивидуальные);
    - обнуляет остаток общего пакета (сгорание неизрасходованного трафика);
    - сбрасывает счетчики личных лимитов (сами лимиты остаются неизменными).
2. Backend публикует асинхронное событие в брокер сообщений.

#### Исключения и альтернативные сценарии: 
- **3a. Первый расчетный период:**
1. Backend пропускает шаг архивации статистики за прошлый период, так как его не существует.

### UC-14: Просмотр статистики потребления
* **Актор:** Участник/Владелец
* **Предусловия:** Группа существует.
* **Постусловия:** Участник/Владелец просмотрел статистику потребления.
#### Основной сценарий: 
1. Пользователь открывает вкладку со статистикой потребления.
2. Мобильное приложение отправляет синхронный REST-запрос в Backend.
3. Backend определяет роль пользователя:
    - Если Владелец: формирует ответ с общей статистикой группы и разбивкой по дням для каждого Участника (BR-12).
    - Если Участник: формирует ответ только с личной статистикой потребления (BR-12).
4. Backend возвращает данные в Мобильное приложение.
5. Мобильное приложение отрисовывает графики и таблицы.

#### Исключения и альтернативные сценарии: 
- **3a. Статистика не собрана (начало расчетного периода или начало пользования системой):**
1. Backend возвращает на отображение пустые графики и колонки.

### UC-15: Просмотр истории изменений состава и лимитов
* **Актор:** Участник/Владелец
* **Предусловия:** Группа существует.
* **Постусловия:** Участник/Владелец просмотрел статистику потребления.
#### Основной сценарий: 
1. Пользователь открывает вкладку с историей изменений.
2. Мобильное приложение отправляет синхронный REST-запрос в Backend.
3. Backend определяет роль пользователя:
    - Если Владелец: возвращает полную историю изменений состава группы и лимитов всех участников (BR-10).
    - Если Участник: возвращает только историю изменения его личных лимитов (BR-10).
4. Backend возвращает список событий (дата, тип действия, инициатор, детали) в Мобильное приложение.

#### Исключения и альтернативные сценарии: 
- **3a. Статистика не собрана (начало расчетного периода или начало пользования системой):**
1. Backend возвращает на отображение пустые графики и колонки.

### UC-16: Авторизация пользователя
* **Актор:** Пользователь (Неавторизованный)
* **Предусловия:** Приложение установлено. Пользователь не авторизован в приложении.
* **Постусловия:** Пользователь авторизован в приложении. Приложение получило и сохранило `access_token` и `refresh_token`.
#### Основной сценарий: 
1. Пользователь вводит номер телефона на экране авторизации и нажимает «Получить код».
2. Мобильное приложение отправляет запрос в Backend с номером телефона.
3. Backend валидирует формат номера.
4. Backend проверяет наличие пользователя в БД. Если пользователя нет, Backend автоматически создает новую запись (авторегистрация).
5. Backend генерирует временный сессионный ID для этого номера и ожидает ввод кода (согласно BR-20, в синтетической среде валидным кодом является "0000").
6. Пользователь вводит код "0000" и нажимает «Войти».
7. Backend валидирует код, генерирует пару токенов (`access_token`, `refresh_token`), сохраняет сессию в БД и возвращает токены приложению.
8. Мобильное приложение сохраняет токены в защищенном локальном хранилище и перенаправляет пользователя на главный экран.

#### Исключения и альтернативные сценарии: 
- **3a. Введенный номер телефона не является российским:**
1. Backend не идет дальше по сценарию.
2. Система предлагает пользователю изменить номер телефона.
- **6a. Пользователь ввел неверный код:**
1. Backend сравнивает код и понимает, что он не равен "0000".
2. Backend возвращает ошибку `INVALID_CODE`.
3. Приложение показывает ошибку "Неверный код" и предлагает ввести код еще раз.
* **6b. Истекло время действия кода:**
1. Backend возвращает ошибку `CODE_EXPIRED`.
2. Приложение блокирует поле ввода и делает активной кнопку "Запросить код".
3. После нажатия кнопки "Запросить код", поле ввода становится активным.
- **6с. Превышено количество попыток ввода:**
1. После 3 неудачных попыток Backend возвращает ошибку `MAX_ATTEMPTS_EXCEEDED` и блокирует возможность ввода кода для этого номера на 5 минут.
2. Мобильное приложение показывает таймер обратного отсчета и кнопку «Запросить новый код» (которая станет активной только по истечении времени).

### UC-17: Выход из аккаунта
* **Актор:** Пользователь
* **Предусловия:** Пользователь авторизован в приложении.
* **Постусловия:** Пользователь не авторизован в приложении.
#### Основной сценарий: 
1. Пользователь открывает меню профиля и выбирает «Выйти из аккаунта».
2. Мобильное приложение отображает диалоговое окно подтверждения: «Вы уверены, что хотите выйти?».
3. Пользователь подтверждает выход.
4. Мобильное приложение отправляет запрос в Backend на завершение сессии.
5. Backend аннулирует текущий access-token и refresh-token пользователя в БД.
6. Мобильное приложение очищает локальное хранилище (удаление токенов, кэша группы).
7. Мобильное приложение перенаправляет пользователя на экран авторизации (UC-16).

#### Исключения и альтернативные сценарии:
- **3a. Пользователь отменяет выход:**
1. Мобильное приложение закрывает диалоговое окно.
2. Сценарий прерывается, пользователь остается в приложении.
- **5a. Проблема с сетью при запросе к Backend:**
1. Backend не получает запрос (или возвращает 5xx).
2. Мобильное приложение принудительно очищает локальные токены и все равно перенаправляет пользователя на экран авторизации (чтобы не блокировать выход из-за проблем с сетью).
