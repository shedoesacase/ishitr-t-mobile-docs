# 1. Введение и цели

Генератор — это внешний инструмент для генерации синтетических данных, имитирующий работу реальной телеком-сети. 
Основные цели использования:
- Тестирование бизнес-логики и корректности расчетов (списание баланса, проверка лимитов).
- Проверка временных триггеров и фоновых задач (смена расчетного периода, детекция аномалий) без ожидания реального времени.
- Демонстрация работы системы и отрисовки графиков статистики.

# 2. Режимы работы генератора

- **2.1. Фоновая генерация (Реальное время):** 
  Генератор создает события через фиксированный интервал, передаваемый по API. Событие потребляет в пределах 5-10 Мб трафика и/или минуты разговора, равные длительности промежутка между событиями (В случае, если промежуток меньше минуты - события складываются и потребляются по накоплению минимум минуты).

- **2.2. Ускорение времени (Virtual Clock):** 
  Генератор глобально ускоряет время для всей системы. Режим применяется ко всем сервисам Backend, базам данных и фоновым планировщикам одновременно.
  Связь времени генератора и сторонних сервисов происходит через брокер сообщений.
  *Архитектурное ограничение:* Персональное ускорение времени для отдельных пользователей или групп не поддерживается ввиду критического усложнения архитектуры (необходимости передачи контекстного времени в каждый SQL-запрос и фоновую задачу). Для изоляции тестовых сценариев рекомендуется использовать отдельные развертывания Backend-сервиса. Коэффициент ускорения выставляется вручную через интерфейс Генератора.

- **2.3. Мгновенные действия (Ручное управление):** 
  Режим для быстрого smoke-тестирования. Включает в себя:
  - Отправку пачки событий/одного события для мгновенного изменения баланса (симуляция потребления за месяц за секунду).
  - Ручной триггер специфичных событий (аномальный скачок, запоздалое событие).

- **2.4. Массовая генерация:** 
  Режим для комплексного тестирования, имитирующий одновременную активность всей базы абонентов. Администратор задает единые параметры генерации (режим, интервал/профиль, тип ресурса), которые применяются ко всем активным пользователям системы. При запуске массовой генерации Генератор проверяет список уже активных задач. Пользователи, у которых уже запущена фоновая генерация или аномалия, **игнорируются** — их существующие потоки не прерываются и не перезаписываются. Новая генерация запускается только для "свободных" пользователей. Это обеспечивает сохранность уже идущих тестовых сценариев (например, запущенных аномалий).
  **Пример:**
  - В системе 10 пользователей.
  - У 3 пользователей уже запущена фоновая генерация.
  - Админ запускает массовую генерацию.
  - Генератор запускает новые потоки для 7 "свободных" пользователей.
  - 3 пользователя с активными задачами игнорируются.
  - UI показывает: "Массовая генерация запущена для 7 пользователей. 3 пользователя проигнорированы (уже активны)".

# 3. Архитектура и интеграция

- **3.1. Взаимодействие с Backend:** 
  - **Управление и справочники:** Взаимодействие через REST API (создание тарифов, управление временем, чтение списка активных пользователей и групп).
  - **События потребления:** Генератор публикует события (ConsumptionEvent) напрямую в Брокер сообщений (согласно UC-04), откуда их забирает Backend-обработчик.

- **3.2. Требование к Backend (Паттерн Virtual Clock):** 
  Время внутри системы является синтетическим и единым. Использование стандартных системных функций времени (например, `NOW()` или подобное) строго запрещено. Все компоненты, зависимые от времени (токены сессий, расчетные периоды, TTL кодов авторизации, планировщики), должны получать текущее время через единый внутренний сервис, управляемый Генератором.
- **3.3. Интерфейс Генератора:** Управление генератором происходит через Web-страницу, по средствам кнопок и полей ввода.

# 4. Генерируемые сущности и сценарии

- **4.1. Справочные данные и пользователи:** 
  - Создание и управление Тарифами (Таблица 6).
  - Генератор должен уметь читать из Backend список активных Пользователей (Таблица 1) и Семейных групп (Таблица 4), чтобы знать, для кого именно генерировать трафик.

- **4.2. События потребления:** 
  Генерация стандартных событий потребления трафика и минут (UC-04) с уникальными `event_id` для проверки идемпотентности (BR-04).

- **4.3. Специфичные сценарии:**
  - **Аномальный рост:** Генерация частых событий за короткий промежуток времени для проверки BR-15 и UC-08. Согласно BR-15, аномальным потреблением считается 15% собственного трафика или 10% группового. При запуске аномального потребления будет выбираться случайное число в пределах от 15 до 50 процентов личного трафика. Таким образом, в некоторых случаях, потребление 15-50% личного трафика должно покрыть кейс с потреблением 10% общего.
  - **Мгновенное списание:** Списание выбранного типа ресурса у выбранного пользователя. В случае, если ресурса в личном/общем лимите меньше, чем есть в в запасе у пользователя/группы, списывается все возможное.
  - **Запоздалые события:** Отправка событий с `event_timestamp` в прошлом для проверки BR-16 и UC-05.
  - **Сценарий "Поездка":** 
	  * **Целевое потребление:** ~20–50 МБ на виртуальные сутки.
	  * **Поведение:** Событий может не быть часами, затем - резкие вспышки (человек открыл карты, мессенджер) по 1-5 Мб.
	  * **Задержки:** Задержки в рамках поездки усиливаются и учащаются. Каждое 3-4 событие в рамках поездки передается с задержкой в несколько минут. 
* **Сценарий "Стандартное потребление:"**
	* **Целевое потребление:** ~300–500 МБ на виртуальные сутки.
	* **График потребления:**
		* **Ночь (23:00 – 07:00) — «Спящий режим»**
	    - _Поведение:_ Телефон лежит на тумбочке. Идут только фоновые синхронизации (почта, мессенджеры, обновления ОС).
	    - _Генерация:_ 1-2 события в час. Объем: 0.5 – 2 МБ.
	- **Утро (07:00 – 09:00) — «Сборы и дорога»**
	    - _Поведение:_ Человек проснулся, читает новости, смотрит погоду, листает ленту соцсетей в транспорте.
	    - _Генерация:_ Высокая частота, средний объем. События каждые 2-3 минуты. Объем: 2 – 10 МБ (текст/картинки) и иногда до 20 МБ (короткие видео в ленте).
	- **День (09:00 – 18:00) — «Работа / Wi-Fi»**
	    - _Поведение:_ Человек на работе или учебе. В 90% случаев телефон подключен к корпоративному/общественному Wi-Fi, который мы не считаем. Мобильный трафик идет только в редких моментах (отправил голосовое в мессенджере, показал карту коллеге).
	    - _Генерация:_ Низкая частота. 1-3 события в час. Объем: 0.5 – 5 МБ.
	- **Вечер (18:00 – 23:00) — «Досуг и дорога домой»**
	    - _Поведение:_ Пик мобильного потребления. Человек едет домой (видео в дороге), а дома может лечь на диван и включить YouTube/Netflix, если нет Wi-Fi, либо активно пользоваться тяжелыми приложениями.
	    - _Генерация:_ Средняя частота, **большой объем**. События каждые 3-5 минут. Объем: 15 – 50 МБ (стриминг видео, тяжелые игры, видеозвонки).

# 5. Ограничения

- **5.1. Код авторизации:** В синтетической среде код авторизации всегда жестко задан и равен "0000" (согласно BR-20).
- **5.2. Финансовые транзакции:** Сервис не генерирует и не обрабатывает реальные финансовые транзакции.
- **5.3. Создание пользователей:** Создание пользователей происходит исключительно через форму регистрации в мобильном приложении (UC-16). Генератор только читает их данные.
- **5.4. Создание семейных групп:** Семейные группы создаются и управляются исключительно через мобильное приложение (UC-01, UC-03).
- **5.5. Управление реальной сетью:** Генератор не управляет реальной сетью, реальными тарифами и реальными абонентами. Все данные вымышлены.
- **5.6. Генератор не проверяет балансы:** Генератор публикует события в брокер сообщений, не проверяя остаток трафика/минут у пользователей (этим занимается Backend-сервис).
